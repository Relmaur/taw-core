# CLAUDE.md — taw-core

**Project:** WordPress theme framework consumed as a Composer package by theme repos (e.g. taw-theme).

## Commands

| Task | Command |
|------|---------|
| Install deps | `composer install` |
| Scaffold block | `php bin/taw make:block <Name> [--type=meta] [--group=<dir>]` |
| Import block | `php bin/taw import:block <path>` |
| Export block | `php bin/taw export:block <Name>` |
| Static analysis | `composer run phpstan` |
| Unit tests | `composer run test` (Brain Monkey — no real WP install needed) |
| JS tests (shared Vite config) | `node --test tests/js/*.test.mjs` (Node 22+, no npm install) |
| Static site export | `php bin/taw export:static [--dir=<path>] [--prod-url=<url>]` |
| SEO/copy audit — extract | `php bin/taw seo:extract <post_id>\|--all [--output=<path>]` |
| SEO/copy audit — inject | `php bin/taw seo:inject <post_id>\|--all [--input=<path>] [--dry-run]` |
| WP-CLI passthrough | `php bin/taw wp <args>` (auto-resolves Local's socket for PHP and, via `MYSQL_UNIX_PORT`, for `wp db`; + `--path`) |

## Architecture

- `TAW\` → `src/` (PSR-4). No other namespace roots.
- `src/Support/utilities.php` and `src/Support/performance.php` are file-autoloaded. **Loading them must have no WordPress side effects** (ADR-0003): `performance.php` only defines the class — `Performance::register()` is called by `Theme::boot()`/`bootstrapFullSite()` (escape hatch: `TAW_PERFORMANCE_AUTOLOAD`); global helpers in `utilities.php` are all `function_exists`-guarded. `AutoloadSideEffectsTest` enforces both.
- `src/Core/` — framework features (Block, Metabox, Form, OptionsPage, etc.)
- `src/Support/` — infrastructure (ViteLoader, Performance)
- `src/Helpers/` — stateless utility classes (Framework, Image, Svg, Dump)
- `src/CLI/` — Symfony Console commands
- **No templates here** — views live in the consuming theme, not in this package.

## Key Conventions

- **taw/core is for TAW sites only** (taw-theme, taw-gutenberg, and their child themes — ADR-0003 addendum). No third-party/external consumers: design for those two, not for arbitrary plugins.
- **Two entry points (ADR-0003).** `Theme::boot()` is the classic-theme entry point — it wires every subsystem, including the data layer. `TAW\Core\Boot::data()` is the data-only entry point for block/hybrid themes and site plugins: content interchange screen + REST route + REST-registered field meta, nothing presentational. `Theme::boot()` calls `Boot::data()` at step 13; both are idempotent. Anything that dequeues/injects frontend output (Performance, Vite, blocks) must never be wired into `Boot::data()`.
- **Schema (`TAW\Core\Schema\*`, ADR-0004)** — post types/taxonomies/fieldsets/options pages defined on the `taw_schema_register` action (init:1), frozen at init:5, compiled at init:5/6/8 into `register_post_type`/`register_taxonomy`/`new Metabox`/`new OptionsPage` — never a second field engine. Also loadable from `taw-schema/*.json` (`JsonLoader`, hand-written `Validator` — no JSON Schema library; `resources/schema/taw-schema-1.0.json` mirrors it and `JsonSchemaFileTest` keeps them in sync; `bin/taw schema:validate` needs no WordPress). PHP outranks JSON. Wired by `Boot::data()` (`Compiler::register()`). Schema classes omit the ABSPATH guard (`bin/taw` loads them pre-boot; `Schema\PreBootAutoloadTest`). Keep `Field::TYPES` in sync with the Metabox renderer.
- **Editing policies (`TAW\Core\Editing\*`, ADR-0005)** — layered block-editor lockdown (content per post type, site structure, design tokens, editor features; presets `open`/`guided`/`structured`/`locked`). Declared as schema kind `editing` (key `site`) or `PostType::editing()`; `Editing\Rules` is the one validator (PHP builders + JSON `Validator`); `Editing\Resolver` → `Editing\Policy` is pure (order: preset → layer level → keys → post-type rule → site content map; `TAW_EDITING_PRESET` replaces only the preset). **Never wire it into `Boot::data()` or `Theme::boot()`** — only `Boot::editing()` (v1.46.0; `TAW_EDITING_OFF` = no-op) wires it: `Editing::apply()` at init:7 (after the registry freezes at 5, before core patterns at 10) hooks `Bypass` (`user_has_cap` grant for `TAW_EDITING_BYPASS_USERS`), `ContentLayer` (allow-list + template/lock + `rest_pre_insert_{type}` check that only rejects *newly added* blocks) and `FeaturesLayer`, then (v1.47.0) `SiteLayer` (REST write guard at `rest_pre_dispatch` for templates/template-parts/global-styles/navigation — NOT capability re-mapping, see ADR-0005 addendum), `DesignLayer` (`wp_theme_json_data_theme` explicit `false`s, site-wide, then `wp_clean_theme_json_cache()`), and the read-only `EditingAdminScreen` (Tools → TAW Editing). Template locks and design tokens are editor guardrails; the allow-list and site-structure writes are enforced server-side. **WP 7.1 ignores a root `contentOnly` lock** (ADR-0005 addendum 2): `lock: contentOnly` is sent as `templateLock: all` + `assets/editing-content-only.js` (`setBlockEditingMode('contentOnly')` on every block, re-applied after canvas mount). Any change here needs a real browser check — unit tests and wp-cli only see the settings, not how the editor enforces them. Policy key `themeBlocks` (v1.50.0, ADR-0005 addendum 3) is appended by the Resolver to every content rule whose `allow` is a list (never to `null`), after the resolution order. `PresetsTest` pins the preset table; changing a preset is a deliberate, changelogged act. Keep `resources/schema/taw-schema-1.0.json` in sync (`JsonSchemaFileTest`). Editing classes omit the ABSPATH guard.
- **Vite: two classes (ADR-0006).** `TAW\Support\ViteLoader` is the classic toolkit (taw-theme; `Theme::boot()` calls `init()`). `TAW\Core\Assets\Vite` is the theme-agnostic adapter for block themes and packages (`Vite::theme()` / `new Vite($dir,$url)`; `script()`, `style()`, `url()`, `block()`); it's never booted automatically and adds no hooks until used. Both detect dev mode only through `Assets\DevServer` (hot file → verified `/@vite/client`; no default-port fallback), so don't reimplement the probe. `Assets\Vite` marks modules via `wp_script_attributes` (never a `script_loader_tag` rewrite). Shared Vite config for themes: `resources/vite/taw-vite.mjs` (`wordpressExternals()` with the one `WP_EXPORT_NAMES` list, `hotFile()`, `phpReload()`), tested by `node --test tests/js/*.test.mjs` (no npm deps).
- **Data panel (`TAW\Core\DataPanel\*`, ADR-0007; v1.51.0)** — a fieldset shows in the block editor's "TAW Data" sidebar **or** as a metabox, never both (the metabox's later form post would overwrite the panel's REST save). `Ui::resolve()` order: fieldset `ui` → `TAW_DATA_UI` → schema kind `settings` (`fieldsetUi`) → `metabox`. `Boot::data()` → `DataPanel::register()`: one `init:999` check that removes itself unless something resolves to panel (keep it that way: the golden snapshot depends on it). `Metabox::register()` asks `taw_metabox_ui` before `add_meta_box()`; `Metabox::instances()`/`appliesTo()` feed the panel. `Descriptor` is the only browser contract (JSON, no callables; bindings `meta` key or `taw_<id>` field; group subs `{prefix}{group}_{sub}`, repeater subs unbound); an unsupported type keeps the whole fieldset a metabox. `Validation` mirrors `Metabox::save()` on REST (`rest_pre_insert_{type}` → 400 `taw_data_invalid` with `data.fields`; readonly refused only when changed (the editor resends the whole meta object each save, so an unchanged read-only value is dropped from the write via `Validation` `drop`); hidden-by-conditions skipped and cleared in `rest_after_insert_{type}`; autosaves never refused). **The panel UI** is TSX in `resources/data-panel/` (own `package.json`; `npm run check` = lint + format + tsc + Vitest + build) built into **committed** `assets/data-panel/` (CI fails if it differs from a fresh build — rebuild and commit it with every source change); `DataPanel::enqueueAssets()` loads it via `new Assets\Vite(Framework::path(), Framework::url(), 'assets/data-panel')`, and `npm run dev` there (port 5175) takes over through `assets/data-panel/hot`. Descriptor reaches JS as `select('core/editor').getEditorSettings().tawDataPanel`; values edit through `editPost` (meta merged, `taw_<id>` top-level), so they save with the post. Controls mirror core's sidebar look (color = theme palette via `core/block-editor` settings `colors`). P3 controls: image/files via `MediaUpload` + core-data `getEntityRecord('postType','attachment')` (not the deprecated `getMedia`); icon via `taw/v1/icons` (descriptor `icons` = `Lucide::isEnabled()`; the endpoint comes from `Lucide::init()`, which is idempotent and called by both `Theme::boot()` and, since v1.51.1, `Boot::data()`); post_select via core `wp/v2/search` (published only, like the metabox; not `taw/v1/search-posts`, which only taw-theme registers); gradient_text/hubspot_form as JSON strings in meta; multi-part fields render in `FieldGroup` (framed card). **wysiwyg = a mini block editor in a modal** (`rich/`): load = `autop()` → `rawHandler()`; save = `serialize()` minus `<!-- wp: -->` delimiters → `removep()`, i.e. **the same format `wp_editor()` stores** (no `<p>`), so raw-printing and `wpautop()` templates both render as before; opening/cancelling never writes. Nested `BlockEditorProvider` + `BlockCanvas` (iframed, theme editor styles): re-check in a browser after WordPress upgrades. P4: `group` = `FieldGroup` of bound sub-fields (conditions see `{group}_{sub}`); `repeater` = collapsible row cards over the decoded `taw_<id>` rows via the unbound `ControlFor` (row conditions: siblings first, then the fieldset's fields, as the metabox), `min`/`max`/read-only, nested repeaters; a group inside a repeater keeps the fieldset a metabox. `SaveLock` (rendered outside the sidebar) calls `lockPostSaving('taw-data-panel')` + a notice while a shown required field (top-level or group sub; never repeater rows, as the server) is empty; failed saves (`getLastEntitySaveError`, code `taw_data_invalid`) and, once dirty, empty required fields get a red mark. `Metabox::enqueue_admin_assets()` skips fieldsets placed in the panel. **`Metabox::sanitizeRepeaterRows()`** (REST, panel, visual editor, `fields:set`, importer) now matches the form save: sub-values via `sanitizeForStorage()`, nested repeaters stored as arrays, `max`, empty rows dropped (before P4 it blanked nested repeaters and files/post_select inside rows). `FieldMetaRegistrar` scalar meta also sanitizes with `sanitizeForStorage()` (so REST writes of `gradient_text`/`hubspot_form` get the metabox's normalization).
- Blocks auto-discovered from theme's `/Blocks` directory at `after_setup_theme`.
- `registerMetaboxes()` is deferred to `init` by the framework — `__()` calls are always safe inside it.
- `getData(int|false $postId)` — `$postId` is `false` on 404 pages; all meta helpers (`getMeta`, `getImageUrl`, `getRepeater`) return safe empty values for `false`.
- Repeater and `files` field values are stored as JSON strings — callers must `json_decode()`.
- Use `Metabox::get()` and `OptionsPage::get()` as the read API; don't call `get_post_meta()` / `get_option()` directly for framework-managed fields.
- All registered metabox fields are visual-editor-enabled by default. Use `'editor' => false` to explicitly opt a field out.
- **Visual editor is opt-in.** Call `VisualEditor::enable()` in the theme's `functions.php` before `Theme::boot()`. Without it, `isActive()` always returns false and nothing renders.
- When the visual editor is active, `MetaBlock::render()` automatically wraps every block's output in `<div data-taw-block-section="{id}">`. The editor panel groups fields by block ID (matching the section attribute). Live text preview works via text-node content matching — no template annotations required for basic use.
- **Headless CORS is opt-in.** `TAW\Core\Rest\Cors::register()` (wired into `Theme::boot()`) is a no-op unless `TAW_HEADLESS_ORIGINS` is defined in `wp-config.php` — needed only once a `export:static` bundle is served from a different domain than this WordPress install.
- **SEO meta (`TAW\Core\Seo\SeoMeta`) always registers, but stands entirely down if any known SEO plugin (Yoast, RankMath, SmartCrawl) is active** — no duplicate `<title>`/`<meta name="description">`/OG tags, no competing admin UI. Yoast specifically gets read/write support (`SeoMeta::targetMetaKeys()` resolves to its meta keys); other plugins just cause TAW's own output to stand down, without write support for their own keys yet. Covers non-singular contexts too (home, archives, search), not just posts/pages. Per-post `noindex` is a checkbox field, applied via the `wp_robots` filter rather than a hand-printed `<meta name="robots">` tag.
- **Content interchange (`TAW\Core\Content\*`) — the portable snapshot / change-set subsystem, a whole-site *state* migration path.** `Exporter::snapshot($scope)` builds a `json_encode`-ready array: posts (+ `author` as `{login,email}`, `comment_status`/`ping_status`, `_taw_*` fields), `_taw_*` options + a core allowlist, terms, referenced media; **opt-in** `users` (`--with-users`, hashes only with `--with-user-passwords`), `comments` (`--with-comments`), environment settings (`--with-settings` + `taw_content_export_settings_options` filter), unreferenced media (`--all-media`), drafts (`--include-drafts`). `--migrate` = `--with-users --with-settings --all-media --include-drafts`. `Importer::plan()` is a mandatory zero-write dry run; `Importer::apply()` writes a **maximal-scope** rollback snapshot to `uploads/taw-private/` first, then applies in dependency order **users → terms → media → posts → comments → settings**. Records matched by natural key (post `type`+`slug`, or `type`+`match_key` for slug-less drafts; option key; term `taxonomy`+`slug`; user login→email; comment content-hash) — never numeric ID. Also auto-exports any CPT with a `Metabox` attached (`Metabox::postTypesWithMetabox()`), not just `public => true`. `FieldCodec` is the pure decode/attachment-ref layer (unit-tested without WP). CLI: `content:export` / `content:import` (`--with-settings` gates settings on import too) / `content:diff` (diffs `users`/`comments` too). **The `Content\*` class files deliberately omit the `if (!defined('ABSPATH')) exit;` guard** — the `content:*` commands autoload them before booting WordPress, and the guard's `exit` silently kills the command (v1.25.1). They're pure class defs, same as `Framework`/`WpLoader`. Portable transforms (`page_on_front`/`page_for_posts`/`sticky_posts` ↔ slug, `parent` ↔ slug, `featured_media` ↔ filename, `author` ↔ `{login,email}`) are reversed on import; a clean `--migrate` export→import is a verified no-op (0 created/updated/deleted). Schema: `resources/schema/content-interchange-1.2.json` (importer accepts `1.0`–`1.2`; 1.2 keys `_taw_` fields by bare id and other prefixes by full meta key, via the pure `Content\FieldKeys`). `GET taw/v1/content/export` stays content-only. Wired default-on by `Boot::data()`, which `Theme::boot()` calls at step 13 (Tools → TAW Data screen, the REST route, and `FieldMetaRegistrar` — REST-registered field meta; `add_filter('taw_register_meta_in_rest', '__return_false')` opts out the last).
- **Qualified field registry (ADR-0008, v1.52.0).** Besides the bare `$fieldRegistry` (kept as is for `get_field_config()`/`Metabox::get()` callers; last wins), every field is indexed as `"{metabox id}.{field}"` (group subs `"{id}.{group}_{sub}"`) with `qualified_id`, `field_key`, `meta_key`. **Map meta keys to configs with `Metabox::fieldsFor('post', $type)` / `fieldFor()` / `fieldMatches()`, never with a bare id**: `FieldMetaRegistrar`, `Exporter`/`Importer`, the data panel's stored reader, `VisualEditorEndpoint`, `fields:get`/`fields:set` (`TAW\CLI\FieldRef`) and `inspect` do. `Metabox::metaKeyOf()` prefers `meta_key` (a bare group-sub config's `id` is the sub id — writing with it used to hit `_taw_{sub}`). Tests reset with `Metabox::resetRegistryForTests()`.
- **Storage contexts + term fieldsets (ADR-0008, v1.53.0).** The metabox engine reads/writes values only through `Metabox\Store\MetaStore` (`PostMetaStore`/`TermMetaStore`/`UserMetaStore`; `$this->store` is set by each entry point: `render()`, `save()`, `render_term_add()`/`render_term_edit()`/`save_term()`), and `render_fields_container()` + `save_fields()` are shared by posts and terms. **The post path must stay byte-identical**: before touching the engine, capture the rendered HTML of a post metabox with every field type and a `$_POST` save log (writes short-circuited via `update/delete_post_metadata`) on the `taw` site, and compare after. `"term:<taxonomy>"` screens are excluded from `parseScreens()`/`screensToPostTypes()` (else they'd read as page slugs) and resolved by `screensToTaxonomies()`; term hooks are only added when a fieldset has term targets (golden snapshot). `FieldMetaRegistrar::registerTermMeta()` is called from `registerPostMeta()` (no new hook). Term Add screens post over AJAX (tags.js, which in WP 7.1 skips `validateForm`): `print_term_add_script()` validates required fields, flushes repeaters/TinyMCE in a capture-phase click, and reloads with `?message=1` after a successful add. Term screens lay fields out with flex (`admin.css` `.taw-term-fields`): the 100-column grid's 99 gaps need ~792px. Readers: `Metabox::get_term()` / `Metabox::term($id)` (`FieldReader`). `Metabox::writeTo($store, …)` is the store-generic `writeMeta()`.
- **User fieldsets (ADR-0008, v1.54.0).** `"user"` in screens (never a page slug; excluded from `parseScreens()`/`screensToPostTypes()`) → `render_user_edit()` (`show_user_profile`/`edit_user_profile`), `render_user_new()` (`user_new_form`, `add-new-user` context only), `save_user()` (`personal_options_update`/`edit_user_profile_update`/`user_register`; nonce + `edit_user`). Hooks only when a fieldset targets users. Errors → transient `taw_validation_errors_user_{id}`, shown by `displayValidationErrors()` on profile.php / user-edit.php / users.php?update=add&id=. **REST user fields are `edit`-context only** (`show_in_rest.schema.context = ['edit']`, `taw_<id>` schema context edit + a capability check in `get_callback`): `/wp/v2/users/<id>` is public for authors. `Metabox::fieldsFor('user')`, `get_user()`/`user()`. Interchange: user records gain `fields` under `--with-users`.
- **Options pages over REST (v1.55.0), opt-in per page.** `rest: 'private'` → `register_setting(show_in_rest)` (schema types from `FieldMetaRegistrar::SCALAR_REST_TYPE`, JSON types as their raw string) so the options show in `/wp/v2/settings` (manage_options), with the form's `validate_field()` run on writes at `rest_request_before_callbacks` (400 `rest_invalid_param`); `rest: 'public'` also adds `GET taw/v1/options/<page id>` (anyone; `FieldCodec::decode()` per field). Only pages with `rest` hook `rest_api_init` (golden snapshot); `register_settings()` runs once per request. `REST_MODES` lives on the pure `Schema\Definition\OptionsPage` (pre-boot autoload).
- **Text domain `taw-core` (v1.56.0).** Every translatable string in taw-core uses `'taw-core'` (literal strings only); the only other domain in src/ is the theme's own (`Theme::bootstrapFullSite()`'s `load_theme_textdomain('taw-theme')`, and the block code `MakeBlockCommand` writes into themes). `I18n\Translations::register()` (from `Boot::data()`) sets the registry's custom path to `languages/` (lazy load, no hook) and adds the four `*gettext*_taw-core` filters: the theme's `taw-theme` translation wins, else the bundled one. `Translations::mofile()` (`load_textdomain_mofile`) renames WordPress's in-theme guess `{locale}.mo` to `taw-core-{locale}.mo` in our `languages/` (v1.59.2; classic themes keep taw-core in the theme's `vendor/`, and the bundled file never loaded there before). The data panel gets `Translations::scriptLocaleData()` inline. After changing strings: `composer run i18n:pot`, `i18n:po`, translate, `i18n:compile`; CI runs `i18n:check` (`tools/i18n.php`, dependency-free; the .pot has no dates or line numbers).
- **Typed value API (ADR-0009, v1.57.0; terms/users/options v1.58.0).** `TAW\Taw::post()`/`term()`/`user()` → `Core\Fields\{Post,Term,User}Fields` (`MetaFields`: `field($ref)` resolves via `Metabox::fieldFor()`, group parents via their sub-fields' `parent_group`, else untyped `_taw_<id>`; memoized per reader); `Taw::option()`/`options($page)` → `OptionFields` (options registry by option name or id, `_taw_` first; groups via `OptionsPage::getGroupRegistry()`) → `Value` (`raw()`, `value()` = `FieldCodec::decode()`, typed accessors, `__toString()` = `html()` escaped per type) + `Image`, `PostRef`, `Rows`/`Row`. Never throws; type mismatches → `_doing_it_wrong()`. No hooks. `MetaBlock::fields()`. The static helpers stay untouched.
- **`link` field type (v1.59.0).** Stored as JSON `{url, label, new_tab}` or `''` without a URL (`Metabox::sanitizeLinkValue()`, used by every sanitize path); structured (`FieldCodec::STRUCTURED_TYPES`, decodes to the object or null), so REST has `taw_<id>` and the data panel binds it. `required` means a URL (metabox/options `validate_field()`, `DataPanel\Validation::isEmpty()`, `required.ts`). The URL input is `type=text inputmode=url` (a url input blocks relative paths on submit) and comes first (term Add `validateForm()`); its hidden input's change event must bubble or repeater rows don't re-serialize. `Value::link()` → `Fields\Link`.
- **Block Bindings (`TAW\Core\Bindings\*`, ADR-0010, v1.60.0).** `Bindings::register()` (last in `Boot::data()`) registers the `taw/field` source on `init` (`uses_context` postId/postType). `getValue()` → `Reference` (args `field`, `from` post|option|term|user, `sub`, `size`) + `BindingContext` (block `postId`, else the queried post) + `Target` (block × attribute → kind text|plain|url|id|target|rel|date; known core attributes, else guessed from the attribute schema) → `ExpressionResolver` (`FieldResolver`: `Taw::*` readers, privacy as core/post-meta, registered fields only, user fields need `bindings: true`, others opt out with `bindings: false`) → `AttributeMap::valueFor()` (field type × kind; `null` keeps the saved content, `false` removes an HTML attribute). Rich-text targets get HTML (WordPress applies `wp_kses_post`), so text arrives `esc_html`'d; attribute targets arrive unescaped (the tag processor escapes). Read-only: no `setValues`. **Editor (v1.61.0):** `Bindings::register()` also hooks `rest_api_init` (`PreviewEndpoint`, `POST taw/v1/bindings/preview`: `edit_posts`, per post `edit_post`, a template's post type → its latest post) and `enqueue_block_editor_assets` (`enqueueEditor()`: the `bindings` entry of the committed data-panel build, via `DataPanel::assets()`, with `window.tawBindings` = `EditorFields::all()`). The JS (`resources/data-panel/src/bindings/`) registers the source with `getValues` (a `taw/bindings` data store whose resolver batches previews into one POST per tick; field label as placeholder) and `getFieldsList` (typed `string`/`number`); previews refresh after each non-autosave save (the subscriber must update its state before dispatching, or it recurses). `toolbar.tsx` (an `editor.BlockEdit` filter adding a `BlockControls group="other"` `ToolbarDropdownMenu`, "TAW field") and `menu.tsx` (a `registerPlugin` filling `BlockSettingsMenuControls`) adds "Connect to TAW field…" / "Disconnect TAW field" to the block Options menu; `planFor()` maps field type × block to the attributes one pick binds (mirrors `AttributeMap`). WordPress calls `getFieldsList`/`getValues` inside `useSelect`: they return cached objects for equal results (as must any selector here), or it warns about unstable values.
- **`Metabox::writeMeta($postId, $fieldConfig, $value)` is the one meta-write primitive** — sanitize (`sanitizeForStorage()`, covering scalars + repeater/files/post_select) + `wp_slash` + `update_post_meta`, matching `Metabox::save()` exactly. `fields:set` and `Content\Importer` both use it; don't hand-roll `update_post_meta` for framework fields.
- **Security hardening (`TAW\Core\Security\Hardening`) is default-on, not opt-in.** `Theme::boot()` calls `Hardening::hideUsersEndpoint()`, which removes the public `/wp/v2/users` REST collection + single-user route for anonymous requests (filtered at `rest_endpoints`, so it catches `/wp-json/`, `?rest_route=`, and `/batch/v1` at once). `/wp/v2/users/me` and all logged-in access stay intact. Opt a site out with `add_filter('taw_security_hide_users_endpoint', '__return_false')`. The `?author=N` redirect is deliberately *not* here — it's scaffold-level (`taw-theme` `inc/security.php`).
- **SEO structured data (`TAW\Core\Seo\Schema`) mirrors `SeoMeta`'s plugin-detection stand-down** — emits sitewide Organization/WebSite JSON-LD (configured via its own "SEO Schema" options page), Article JSON-LD on posts, and BreadcrumbList on any singular post/page, rendered once as a single `<script type="application/ld+json">` on `wp_footer` (not `wp_head` — blocks push their own nodes onto the graph during body rendering via `Schema::push()`, e.g. the FAQ block's `Schema::faqPage()` node).

## Don't

- **Don't register forms inside templates.** `admin-ajax.php` never runs templates; the AJAX handler won't exist when the form is submitted. Register in `MetaBlock::boot()` → `add_action('init', ...)`.
- **Don't call `__()` directly in `boot()`.** `boot()` fires at `after_setup_theme` before translations load. Wrap in `add_action('init', ...)`.
- **Don't call `ViteLoader::init()` more than once.** It runs the dev-mode socket check and caches the manifest; re-calling resets state mid-request.
- **Don't add templates or theme-specific logic here.** This is a library; theme code belongs in taw-theme.
- **Don't use raw WP meta/option functions** for framework fields — `get_post_meta` / `get_option` bypass the framework's type coercion.
- **Don't add `'editor' => true` to fields** — that was the old opt-in model. The default is now opt-out; only add `'editor' => false` to exclude a field.
- **Don't forget to update README.md** when changing the public API, adding field types, or changing boot behavior.
